=====================================
Prepared from the existing MySuite application and latest approved UI decisions.
Reference date: November 17, 2026.

INSTRUCTIONS TO THE AI BUILDING THE WEBSITE
------------------------------------------
Create MySuite, an interactive condominium building portal with five role-based
experiences: Resident, Concierge, Manager, Board member, and Technician.
This is an application, not a marketing landing page or a property-listing site.
Reproduce the product character, workflows, permissions, and business rules in
this document. Do not substitute attractive static screens for working forms.

Build a polished, presentation-ready prototype with persistent state. A modern
framework is acceptable, but preserve the behavior and design decisions below.
If a production backend is included, implement it deliberately and explain what
is connected. Never imply a preview action sends a real message or payment.

Current implementation categories:
- FULL PAGE: Dedicated interactive workflow already exists in the source.
- DASHBOARD PREVIEW: A card/modal/local interaction exists, but not a complete
  operational service. Recreate honestly without claiming real integrations.
- PRODUCTION REQUIREMENT: Infrastructure or hardening needed for a connected
  release; not a claim that the existing prototype already implements it.

The original uses plain HTML, CSS, JavaScript, localStorage, and IndexedDB for
uploaded PDF files. It has no real authentication server, central database,
payment processor, email/SMS service, or live language-model integration.
Do not display the word "demo" anywhere in the application UI. Realistic fictional
sample content is encouraged. Keep technical implementation details out of the
normal resident flows unless they help the person make a meaningful decision.

1. PRODUCT PURPOSE, BRAND, AND USERS
===================================
Name: MySuite.
Tagline: A little closer to home.
Example building: The Point on the Bow.
Context: A residential condominium building in Calgary, Alberta, Canada.
Currency: CAD. Use readable rates such as $20 and $120 per day.
Scheduling timezone internally: America/Edmonton, with daylight saving handling.
Do not repeatedly display "Calgary time" in Amenities; those labels were removed.

MySuite combines resident services and building operations:
- Residents book amenities, request repairs, reserve the service elevator, report
  absences, read announcements/documents, and find approved building contacts.
- Concierge staff handle packages, incidents, shift logs, maintenance, residents,
  elevator schedules, and absence notices.
- Managers oversee operations, publish announcements, and manage contractors/PDFs.
- Board members view community/board information and publish announcements.
- Technicians see work orders, parts, systems, completed work, and manager notes.

Entry screen:
- A centered MySuite role-selection card with icons and role/account information.
- Five role choices open the appropriate dashboard.
- Log out returns to role selection.
- Example resident account: Maria Santos, Suite 101.
- In the original this is role switching, not password-based authentication.
  Replace with real authenticated accounts for a production implementation.

2. VISUAL DESIGN SYSTEM
=======================
Overall style is warm, calm, residential, readable, and refined. Use a cream page,
dark brown sidebar, caramel actions, light paper cards, warm fine borders,
subtle shadows, rounded corners, outline icons, and photographs of actual spaces.
Avoid a generic blue SaaS dashboard, oversized shadows, excessive whitespace,
unrelated glass effects, or decorative gradients that change the product identity.

Reference colors:
  Cream page background: #F8F4EE
  Paper/cards: #FFFCF8
  Sand: #E9DED0
  Primary caramel: #A66B38
  Dark caramel/hover: #855027

  Inactive tab text/icons: #665B52
  Inactive tab count background: #F1E8DD
  Completed/available: dark green on pale green
  Cancelled/unavailable/error: dark red on pale red

Typography:
- Page titles use Georgia or a close serif, weight 500, line-height about 1.12.
- Desktop title size: clamp(33px, 3.2vw, 54px), tracking about -1.8px.
- Existing responsive title sizes: 40px at <=1200px, 38px at <=800px, 34px at
  <=480px. Preserve a balanced readable result rather than blindly shrinking.
- Interface text uses a system sans-serif similar to Segoe UI.
- Page descriptions: 14px, line-height 1.45, dark brown #3D2A1C.
- Match page title/description styling to the Long-term absence page throughout.
- Announcements title/description placement matches Amenities, about 28px top
  and 18px bottom header padding. Do not move Amenities to fix Announcements.
- Sidebar links, name, subtitle, initials, and logout: 14px on every role/page,
  including narrower desktop screens.
- All Contact directory text must remain at least 14px.
- New form controls, filters, statuses, and secondary text should generally stay
  at least 14px. Do not recreate tiny screenshot text that is hard to read.

Shapes and interaction styling:
- Main cards: around 20px radius; controls: around 7–10px.
- Fine warm borders and modest shadows.
- Filled caramel primary buttons; outlined secondary buttons.
- Red destructive actions where cancellation/removal is offered.
- Statuses have text and/or icons as well as color.
- Use restrained keyboard focus borders. Do not add thick brown rings around
  text fields or page selectors. Keep an accessible focus indication.
- Make forms compact and practical, with aligned labels and consistent gaps.

4. ROLES AND PERMISSIONS
========================
Announcements:
- Every role may read announcements and open full details.
- Only Manager and Board member may compose/publish.
- Resident, Concierge, and Technician are read-only.

Approved contractors:
- Every role may view contractor information and uploaded documents.
- Manager alone may add/edit contractors, upload PDFs, and remove documents.
- Other roles get View more details rather than Edit.
- No expiry functionality or private per-document sharing states in this scope.

Privacy:
- Residents cannot browse other residents' private directory/contact information.
- Resident directory views show building contacts and approved contractors.
- The current staff/board pages have broader resident-directory views. Enforce
  their intended permissions with a backend in a connected release.
- Resident requests/bookings must be scoped to the current account/suite.
- Residents cannot cancel another resident's request or reservation.
- Client-side hidden buttons are not production security. Enforce permissions
  on reads, writes, status transitions, and file downloads server-side.

Timed rules:

- Start earlier than end on the same day; start must be in the future.

COMMON AVAILABLE-WINDOW ENGINE
1. Collect confirmed reservations for every selected timed space on that date.
2. Clip occupied periods to opening hours.
3. Merge overlapping and adjoining occupied periods across selected resources.
4. Subtract those periods from the booking day.
5. Exclude elapsed time for today; the current UI rounds its earliest future
   start to the next 15-minute boundary.
6. Return intervals free for all selected timed spaces.

Example: Pool booked 11 AM–1 PM; Common area booked 4–7 PM.
Shared windows: 8–11 AM, 1–4 PM, 7–10 PM.

Availability panel:
- Compact informative panel with title Available windows, date/resource context,
  small window chips, tight spacing, and no large explanatory block.
- If several windows exist, let the user choose a chip and show selected state.
- If exactly one exists, apply it automatically without a meaningless extra click.
- Applying a window does not automatically select its entire duration.
- If no reservations restrict the selected date and one window remains, hide
  the whole availability panel and apply that window automatically.
- If fully booked, show no-availability feedback and prevent continuing.
- Recompute on date/resource/reservation changes; clear or reconcile invalid
  times while retaining valid choices where possible.
- Start options must be inside the selected window, excluding its end boundary.
- End options must be after start, inside the window, and <= start + eight hours.
- Use 15-minute options plus exact interval boundaries where necessary.
- End stays unavailable until a valid start is chosen.

Availability help:
- Why aren't other times available? sits below window chips.
- Dialog copy: Available windows are times when all selected amenities are free
  and not booked by another resident.
- Show actual reserved periods and resource names if such periods exist.
- Do not show a No reserved periods message when there are none.
- Do not restore the removed Window selected automatically. Choose any duration
  within it, up to 8 hours helper sentence.
- Do not restore visible Calgary time labels.

17. PERSISTENCE AND PRODUCTION LIMITATIONS
==========================================
Current prototype facts:
- Role selector is not real authentication.
- localStorage is browser-local, not a multi-user central database.
- Different devices/browsers do not automatically share records.
- Several pages respond to cross-tab storage changes; this is not server sync.
- Contractor PDFs use IndexedDB; metadata is separate.
- Dashboard financials, occupancy, systems, staff/work details are mostly fixtures.
- Shop orders, payment processing, live AI, email/SMS/push are not connected.
- Calendar is illustrative, not a complete shared calendar backend.
- Some navigation entries remain # links or local previews.
- A success toast in a preview is not proof of a persisted backend operation.

Connected-version requirements:
- Real authenticated sessions and building-scoped permissions.
- Shared database and secure file storage with authorized downloads.
- Shared maintenance lifecycle across resident, concierge, manager, technician.
- Transactional reservation checks; all-or-nothing booking batches.
- Integer money values and stored rate/quantity/fee snapshots.
- Stable identifiers/references and audit information for staff actions.
- Notifications/AI/payment services only if explicitly implemented and tested.
- Handle validation, storage/network failures, retries, and duplicate submission.
